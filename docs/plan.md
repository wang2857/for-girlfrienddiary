# 安卓日记 App 方案

目标：做一个"打开就能写、三年后还翻得动"的私密日记本。功能待定，所以这份文档先定骨架、再定分层，功能按优先级往上叠。

前提假设：单人开发、只做安卓、自己主力使用。如果后面要上架或做多端，见第 9 节。

---

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 产品定位 | 选 **A. 极简速记**（详见 1.1），不做打卡社交、不做云陪伴 |
| 技术栈 | **Kotlin + Jetpack Compose**，原生。不用 Flutter/RN |
| 数据 | 本地 Room/SQLite，**无账号、无后端**，随时能导出成 Markdown |
| 首发范围 | 11 个功能的 MVP，业余 4–6 周 |
| 明确不做 | 云同步、AI、富文本编辑器、社区、订阅 |
| 最大三个坑 | 中文全文搜索、加密与备份互斥、长文输入卡顿 |
| 分发 | 先侧载 APK 自用；上国内商店要软著 + 备案，先别碰 |

一句话取舍：**日记 app 的成败不在功能多少，在"记录摩擦"和"可回看"。** 所有功能都为这两件事让路。

## 1. 定位：先选一个，再谈功能

功能待定的时候，最该先定的是"给谁写、写成什么样"。三种主流形态：

| | A. 极简速记 | B. 心情打卡 | C. 长文写作 |
|---|---|---|---|
| 代表 | Day One 极简版 | Daylio | 格志 / Flomo |
| 核心动作 | 打开→写→关，10 秒 | 点表情+写一句 | 坐下来写 500 字 |
| 结构 | 时间线 | 日历+统计 | 卡片/标签/时间轴 |
| 优点 | 最容易坚持 | 数据感强、适合复盘 | 内容价值高 |
| 缺点 | 容易写成流水账 | 内容薄，久了像打卡 | 门槛高，容易断更 |
| 工作量 | 小 | 中 | 大 |

**推荐 A，但吸收 B 的日历和 C 的标签。** 理由：A 的摩擦最低，最容易变成"每天都会打开"的 app；日历和标签是低成本的增值，不增加记录负担。

### 三条产品原则

1. **低摩擦**：点图标到能打字 ≤ 1 次点击、≤ 1 秒；没有标题也能直接存；草稿自动保存，永不弹"是否保存"。
2. **数据是你的**：本地存储，一键导出 `Markdown + 图片` 的 zip，不绑架、不锁定。
3. **私密默认**：默认不联网；可选 PIN/生物识别锁；进后台遮罩缩略图；只有主动导出才出沙盒。

### 反例（明确不做）

打卡排行榜、关注/评论、模板商城、会员订阅、"AI 陪伴聊天"。这些会把一个工具变成社交产品，和"私密"直接冲突。

## 2. 功能分层

### MVP（第一版必须有，11 项）

1. **快速记录**：新建后直接写；无标题自动取正文首行；草稿 debounce 自动存
2. **时间线**：按 `entry_date` 倒序，按月分组；卡片显示时间、首图、两行摘要、心情
3. **详情与编辑**：基础 Markdown（标题/粗体/列表/引用/分隔线），图片插入
4. **日历视图**：月历上标记有记录的日子，点进去看当天条目
5. **标签**：一条多标签，时间线可按标签过滤
6. **搜索**：标题+正文关键词 + 标签 + 日期范围
7. **图片**：拍照/相册，落地前压缩（长边 2048、JPEG 85），多图九宫格
8. **心情/天气**：各选一个 emoji 即可，可整体关闭
9. **应用锁**：PIN + 生物识别；后台时遮罩 + `FLAG_SECURE`
10. **导出/导入**：zip（md + 图片 + 元数据 json），能导回来
11. **每日提醒**：固定时间通知，点通知直达新条目输入

附带必做的小事：深色模式、字号/行距调节、空状态引导、崩溃日志本地留存。

### V1（MVP 用满一个月后再挑 2–3 个）

- 那年今日 / 随机回顾（怀旧是日记 app 的第二增长点）
- 统计：累计字数、连续天数、月热力图
- 主屏小组件（Glance）：今日写没写 + 一键进入
- 长按图标快捷方式直达输入
- 多日记本（工作/生活/读书分开）
- 语音速记（录音 + 转写）
- 位置/天气自动填充
- 单篇加密（比整库加密轻）
- 导出 PDF / 年度书

### V2（想清楚再做，别提前）

- 同步：WebDAV 或自建服务，端到端加密，先解决冲突策略
- AI：自动标题、摘要、情绪曲线、月度回顾。**必须 BYO API Key + 明示上传范围 + 可单条豁免**
- 多端只读回看（Web）

### 明确不做

社区、评论、关注、模板商城、订阅制、广告。

## 3. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 语言/UI | Kotlin 2.x + Jetpack Compose + Material 3 | 单端原生，动效和输入体验最好调 |
| 架构 | MVVM + 单向数据流（UDF） | 官方范式，单人也能维护 |
| 模块 | **单 module 起步**，包按功能分；痛了再拆 `core`/`feature` | 提前多模块是给自己上刑 |
| DI | Hilt | 少写样板，测试替换方便 |
| 数据库 | Room + SQLite | 迁移可控，Flow 直出 |
| 偏好 | DataStore（Proto/Preferences） | 替代 SharedPreferences |
| 图片 | Coil 3 + 自己写压缩 | 缩略图内存要盯 |
| 拍照 | MVP 用系统相机 Intent + FileProvider | CameraX 自绘相机是 V1 的事 |
| 导航 | Navigation Compose（type-safe） | 类型安全路由 |
| 后台 | WorkManager | 提醒、自动备份、缩略图清理 |
| 异步 | Coroutines + Flow | — |
| 加密 | SQLCipher（`net.zetetic:sqlcipher-android`）+ Keystore | 见 5.2 |
| 测试 | JUnit + Turbine + Robolectric；截图用 Roborazzi | Paparazzi 对 Compose 支持一般 |
| 构建 | Gradle KTS + version catalog + Compose Compiler plugin | — |
| CI | GitHub Actions：lint + test + assembleDebug | 防止改崩 |

### 为什么不上 Flutter / RN

- 单端产品，跨端收益为零
- 要深度接系统：小组件、通知直达、生物识别、屏幕遮罩、SQLCipher、文件导出，原生每个都是一行配置，跨端每个都要写桥
- 冷启动和长列表、长文本输入是日记 app 的体验命门，原生可控性最高
- 包体更小、崩溃栈更好读

真要以后上 iOS，数据和导出格式是 Markdown + SQLite，迁移成本主要在 UI 重写，这个代价可以接受。

## 4. 架构与数据模型

```
app/src/main/java/.../
├── core/            # 通用：时间格式化、Markdown 渲染、图片压缩、Result 封装
├── data/
│   ├── db/          # Room entities / dao / migrations / converters
│   ├── repo/        # EntryRepository / TagRepository / SearchRepo / BackupRepo
│   ├── media/       # 文件落盘、缩略图、清理
│   └── prefs/       # DataStore
├── feature/
│   ├── timeline/    # 列表 + 分组 + 过滤
│   ├── editor/      # 编辑 + 自动保存 + 工具栏
│   ├── detail/      # 阅读态 + Markdown 渲染
│   ├── calendar/    # 月历
│   ├── search/
│   ├── settings/    # 锁、提醒、导出、主题
│   └── lock/        # PIN / 生物识别闸门
└── ui/              # 主题、通用组件、动效
```

### 表结构

```sql
entry(
  id INTEGER PK,
  uuid TEXT UNIQUE,          -- 导出导入去重用
  entry_date INTEGER,        -- 日记归属日（可补写昨天）
  created_at INTEGER,
  updated_at INTEGER,
  title TEXT,
  body_md TEXT,
  mood TEXT, weather TEXT,
  pinned INTEGER, locked INTEGER,
  word_count INTEGER,
  is_draft INTEGER,
  deleted_at INTEGER         -- 软删除 → 回收站
)
tag(id, name UNIQUE, color, created_at)
entry_tag(entry_id, tag_id)  -- 复合主键 + 级联删除
attachment(id, entry_id, kind, rel_path, width, height, bytes, created_at)
```

三个刻意的设计：

- **`entry_date` 和 `created_at` 分开**：晚上 11 点写昨天的日记、补写上周，都要能归到正确的那天。日历和"那年今日"全依赖 `entry_date`。
- **软删除**：误删一条写了半小时的日记，是能让用户卸载 app 的事故。
- **`uuid`**：将来同步/导入合并的唯一依据，现在打上，以后不痛。

正文字体里图片存占位 `![图](attachment:12)`，渲染时替换成图片块，删除条目时按引用清理附件文件。

## 5. 三个关键技术点

### 5.1 中文全文搜索

SQLite 自带分词对中文不友好，这是国内日记 app 的经典坑。四种做法：

| 方案 | 做法 | 中文效果 | 成本 |
|---|---|---|---|
| `LIKE '%词%'` | 直接扫表 | 完全正确 | 几万条内可接受，再大就卡 |
| FTS4 + unicode61 | 建虚拟表 | 中文按整串切，只有整词能命中，不准 | 中 |
| FTS5 + trigram | 需 bundled SQLite + 手写建表（Room 没有 `@Fts5`） | 3 字以上任意子串都能中 | 中，索引体积翻倍 |
| 自切 2-gram 入索引 | 预处理再交给 unicode61 | 可控 | 代码最多 |

**分期方案（推荐）：**

- MVP：`body_md LIKE '%kw%' OR title LIKE '%kw%'`，配合 `entry_date` 索引 + 分页（每页 30）。合起来几十万字以内够用，代码为零。
- 数据破万 / 明显变慢后：上 FTS5 trigram 索引表，2 字查询回退到 LIKE。原文仍存 `entry` 表，索引表只做检索。

不要一上来就集成 jieba 之类的分词库——词典几 MB、还要处理新词和数字，收益远小于先把 LIKE 跑起来。

### 5.2 加密、备份、搜索的三角冲突

三者互相拉扯，是最容易做出"数据打不开"事故的地方。

- **字段级加密会让搜索失效**（密文没法 `LIKE`）。所以选**整库加密**：SQLCipher，搜索照常。
- **密钥**：随机 32 字节 DB key，用 Keystore 里的 AES-GCM 密钥包裹后存 DataStore。**PIN 不直接当密钥**——这样改 PIN 不用重加密全库；PIN 只是 UI 闸门，解锁靠生物识别或设备凭据。
- **备份的坑（重要）**：Android 自动备份（`allowBackup=true`）会把数据库文件传上云，但 **Keystore 里的密钥不备份**。用户换机恢复后，拿到一个永远打不开的库。所以：
  - `android:allowBackup="false"`，并配 `dataExtractionRules` 排除沙盒
  - 备份只走 app 内自己的"导出 zip"和"每日自动导出到本地目录"
- **导出时是明文**：用户要的就是可读文件。落盘到 `Downloads` 或用户选的 SAF 目录，导出后清理临时文件，并在 UI 上明确提示"导出的是明文"。

**取舍建议**：如果只想尽快用起来，MVP 可以**先不加密数据库**，只做应用锁（PIN + 生物识别 + `FLAG_SECURE` 遮罩），V1 再上 SQLCipher。SQLCipher 的代价是包大 ~5MB、依赖商业授权条款、迁移时要做一次全库重写。这条我留给你拍板，默认建议 MVP 就上，因为"日记"这个词本身承诺了私密。

### 5.3 长文输入与自动保存

- `BasicTextField` 绑 `TextFieldValue` 在超长文本（>1 万字）时每次按键都重建，会明显卡。编辑态改用 **String state + 自建选区**，只在必要处同步。
- 自动保存：debounce 800ms 存草稿，`onStop`/`onPause` 强制 flush；进程被杀靠 `SavedStateHandle` 恢复。
- **不要弹"是否保存"对话框**。日记 app 弹一次，用户就少写一次。
- 图片在正文里是占位符 + 缩略图 chip，不把 base64 塞进正文（会让文件爆炸、输入变慢）。
- Markdown 渲染用纯文本编辑 + 预览（`mikepenz/multiplatform-markdown-renderer` 或 Markwon 套 `AndroidView`），工具栏做"加粗/列表/标题/插图"四个按钮就够。**不要做 WYSIWYG**——富文本编辑器是无底洞，见过太多项目死在这里。

## 6. UI 信息架构

底部 3 个 Tab + 一个 FAB：

```
[ 时间线 ]   [ 日历 ]   [ 我的 ]        (+ 新建)

时间线   按月分组，卡片式，粘性月份头，下拉回顶部
         顶部搜索入口；长按进多选（删除/加标签/导出）
详情     沉浸阅读，图片可点开全屏；右上「编辑」
编辑     全屏。顶栏：完成 / ⋯（标签、心情、删除）
         底部工具条：图片 · 标签 · 心情 · Markdown
         返回即保存，不做确认弹窗
日历     月历 + 有记录日的小圆点；上下滑动切月；点日期 → 当天列表
我的     标签管理、提醒、外观、锁、导出/导入、回收站、关于
```

交互上的几个决定：

- **新建即进入编辑，光标已在正文**，标题可选（首行自动当标题）
- 列表卡片两行摘要 + 首图，不给"编辑/删除"小按钮，避免误触
- 删除进回收站，保留 30 天自动清理
- 冷启动做 Baseline Profile + SplashScreen，别让首屏白一下

## 7. 里程碑（业余时间，按 4–6 周估）

| 周 | 内容 | 验收标准 |
|---|---|---|
| W1 | 骨架：Gradle、Compose 主题、Room、条目 CRUD、时间线 | 能写、能看、能删 |
| W2 | 编辑页打磨：自动草稿、Markdown 预览、标签、心情 | 自己愿意天天用它写 |
| W3 | 日历视图、搜索、图片附件 | 翻得到、找得到 |
| W4 | 应用锁、导出/导入、每日提醒、深色主题 | 数据安全且可迁移 |
| W5 | 打磨：动效、空状态、崩溃日志、启动优化、图标 | 连续用一周没有痛点 |

判断"MVP 做完了"的标准不是功能清单全打勾，而是：**你连续两周每天用它写，没有一次因为卡顿/丢失/麻烦而放弃。**

## 9. 需要你拍板的 5 件事

1. **只自己用，还是要上架？** 影响：隐私政策、备案、多用户、崩溃上报。
2. **要不要多设备/云同步？** 影响：数据层是否一开始就做 uuid + 冲突策略（我建议先不做，但 uuid 先打上）。
3. **要不要 AI（摘要/情绪/回顾）？** 影响：是否要 API Key 管理、是否要逐条豁免上传。
4. **正文形态：Markdown 还是富文本？** 我推荐 Markdown。
5. **技术栈：Kotlin 原生（推荐）/ Flutter / RN？**

默认答案（按推荐）：只自己用 → 不上架；不做同步；AI 后置；Markdown；Kotlin 原生。

选了默认那套的话，W1 的骨架我可以直接开搭。
